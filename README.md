## 1. Overview

Digital signatures provide mathematical verification of data authenticity and integrity across untrusted communication channels. When a message or file is transmitted across a network, standard transport mechanisms cannot prove who created the data or whether it was altered after creation.

This project implements an end-to-end **Digital Signature Verification System (DSVS)** designed for Cryptography and Network Security coursework. It utilizes **RSA-PSS** (Probabilistic Signature Scheme) with **SHA-256** digests to sign messages and arbitrary binary files. The application supports verification across three modalities: a browser-based web dashboard, standalone command-line scripts, and a threaded TCP client/server network interface with optional Transport Layer Security (TLS).

---

## 2. Objectives

- Demonstrate the mathematical and operational principles of asymmetric public-key cryptography.
- Implement secure cryptographic hashing and signing standards conforming to **NIST FIPS 180-4**, **FIPS 186-5**, and **RFC 8017 (PKCS #1 v2.2)**.
- Provide practical simulations of real-world cryptographic attacks (tampering, key substitution, timestamp forgery, replay attacks).
- Contrast transport-layer security (TLS) with application-layer authenticity (digital signatures).
- Maintain an auditable event record for forensic validation of cryptographic operations.

## 3. Security Services

| Security Service | Cryptographic Mechanism | Implementation Details |
|---|---|---|
| **Data Integrity** | SHA-256 Digest | Any single-bit change in the message produces an uncorrelated SHA-256 hash, causing verification to fail. |
| **Authentication** | RSA-PSS Signature Verification | Mathematical proof that the signature was generated by the private key corresponding to the verified public key. *(Distinguished from real-world identity verification; see [Public-Key Trust](#18-security-considerations).)* |
| **Non-Repudiation (Cryptographic)** | Asymmetric Private Key Possession | Provides cryptographic evidence linked to the control of the signing private key. *(Legal non-repudiation depends on key governance, legal jurisdiction, and PKI infrastructure.)* |
| **Replay Protection** | Signed Nonce + Timestamp + State Store | Packages bind a Unix timestamp and a 128-bit random nonce. Receivers reject expired timestamps and track nonces in a state store. |

## 5. Key Features

- **Standard-Compliant Cryptography:** Implements RSA-PSS with SHA-256 and MGF1-SHA256, strictly rejecting obsolete algorithms (MD5, SHA-1, PKCS#1 v1.5 padding).
- **Enforced Key Strength:** Restricts key sizes to $\ge 2048$ bits (supporting 2048, 3072, and 4096 bits); keys below 2048 bits are rejected.
- **Password-Protected Keys:** Supports encrypted private key serialization via PEM passphrases (using `BestAvailableEncryption`).
- **Arbitrary File Support:** Signs and verifies plain text as well as arbitrary binary files (e.g., PDFs, executables, images, archives) up to 50 MB.
- **Replay Protection Engine:** Combines signed timestamps, cryptographically secure 128-bit nonces, max-age freshness validation, and a stateful nonce store.
- **Attack Demonstrations:** Dedicated simulation flags for message tampering, signature corruption, key substitution, and replay attacks.
- **Dual Transport Security:** Combines application-level RSA-PSS integrity with transport-level TLS encryption.
- **Structured Audit Logging:** Records every cryptographic event (sign, verify, keygen, error) with UTC timestamps and peer metadata.

## 7. Web Interface

Start the Flask application:

```bash
python app.py
```

Access the interface at **`http://127.0.0.1:5000`**.

```
┌────────────────────────────────────────────────────────────────────────┐
│               Digital Signature Verification System                    │
│   [🔑 Create Keys]    [✍️ Sign]    [✅ Verify]    [📋 Audit Log]        │
└────────────────────────────────────────────────────────────────────────┘
```

### Tab Functionality

1. **Create Keys:** Generates RSA key pairs (2048, 3072, or 4096 bits). Keys are generated in memory on request and returned to the browser session. Private keys are never stored on the web server disk. Provides copy and `.pem` file download buttons.
2. **Sign:** Accepts a PEM private key and either text input or an uploaded file (drag-and-drop). Produces the standardized JSON signature package with metadata display and download capabilities.
3. **Verify:** Accepts a signature package JSON and an optional trusted public key PEM. Evaluates cryptographic validity, computes the message SHA-256 digest, checks age limits, and renders a status badge (`VALID`, `INVALID`, `REJECTED`) along with the decoded message text.
4. **Audit Log:** Displays a live, auto-refreshing tabular view of the last 50 events recorded in `logs/audit.jsonl`.

### API Endpoints

| Method | Endpoint | Description |
|---|---|---|
| `GET` | `/` | Serves the single-page HTML/JS interface |
| `POST` | `/api/keygen` | Generates RSA key pair; payload: `{"bits": 2048}` |
| `POST` | `/api/sign` | Signs data; accepts JSON or `multipart/form-data` |
| `POST` | `/api/verify` | Verifies package; payload: `{"package": {...}, "trusted_public_key_pem": "...", "check_age": 300}` |
| `GET` | `/api/audit` | Retrieves recent audit entries; query parameter: `?n=50` |

## 8. CLI Usage

### 8.1 Key Generation (`keygen.py`)

```bash
# Generate default 2048-bit RSA key pair
python keygen.py --name alice

# Generate 4096-bit RSA key pair with passphrase protection
python keygen.py --name alice --bits 4096 --password

# Specify custom key storage directory
python keygen.py --name bob --keys-dir my_keys
```

### 8.2 Signing Data (`sign.py`)

```bash
# Sign a text message
python sign.py --key keys/alice_private.pem --text "Pay Bob 100"

# Sign a file
python sign.py --key keys/alice_private.pem --file samples/message.txt

# Sign with passphrase-protected private key and custom output path
python sign.py --key keys/alice_private.pem --file samples/message.txt --password --out custom_pkg.sig.json
```

### 8.3 Verifying Signatures (`verify.py`)

```bash
# Verify using a trusted sender public key (Recommended)
python verify.py --package samples/message.txt.sig.json --pub keys/alice_public.pem

# Verify with max-age policy check (reject if older than 300 seconds)
python verify.py --package samples/message.txt.sig.json --pub keys/alice_public.pem --check-age 300

# Verify using only embedded public key (Insecure: lacks sender identity binding)
python verify.py --package samples/message.txt.sig.json
```

## 9. Network Mode

The network mode implements client-server verification over raw TCP sockets using length-prefixed JSON framing (`netproto.py`).

```
┌─────────────────┐       TCP Socket (Port 5050)       ┌─────────────────┐
│     Client      │ ─────────────────────────────────► │     Server      │
│  (`client.py`)  │   [4-Byte Length][JSON Package]    │  (`server.py`)  │
│                 │ ◄───────────────────────────────── │                 │
└─────────────────┘        [Status Response JSON]      └─────────────────┘
```

### Running Network Mode

**Terminal 1 (Receiver Server):**
```bash
python server.py --pub keys/alice_public.pem --port 5050
```

**Terminal 2 (Sender Client):**
```bash
# Normal valid transmission
python client.py --key keys/alice_private.pem --file samples/message.txt

# Tampering attack simulation (Client alters payload bytes before sending)
python client.py --key keys/alice_private.pem --text "Pay Bob 100" --tamper
# Server Result: INVALID — Message SHA-256 mismatch

# Replay attack simulation (Client retransmits identical previous package)
python client.py --key keys/alice_private.pem --text "Pay Bob 100" --replay
# Server Result: REJECTED — Replay detected: nonce has already been used
```

## 10. TLS Mode

Transport Layer Security (TLS) wraps the underlying TCP socket to provide channel confidentiality and protection against eavesdropping in transit.

```bash
# 1. Generate self-signed X.509 certificate and private key
python gen_cert.py
# Outputs: certs/server.crt, certs/server.key

# 2. Start receiver server with TLS enabled
python server.py --pub keys/alice_public.pem --tls-cert certs/server.crt --tls-key certs/server.key

# 3. Transmit payload over TLS tunnel
python client.py --key keys/alice_private.pem --text "Encrypted channel payload" --tls
```

> **Note on TLS Certificates:** `gen_cert.py` generates a self-signed X.509 certificate suitable for local testing. In production environments, certificates must be issued and signed by a trusted Certificate Authority (CA).

## 14. Algorithm Details

### 14.1 Signing Algorithm

```
Input: Raw message bytes M, RSA Private Key K_priv, optional Filename
Output: Signature Package (JSON Dictionary)

1. Read message bytes M.
2. Generate current Unix epoch timestamp: T = int(time.time()).
3. Generate 16 cryptographically secure random bytes:
   nonce = secrets.token_hex(16)   # 32 hexadecimal characters (128 bits of entropy)
4. Compute SHA-256 digest of message:
   H_hex = sha256_hex(M)           # 64 hexadecimal characters
   H_bytes = bytes.fromhex(H_hex)  # 32 raw bytes
5. Construct binary signed content:
   S_content = b"DSVS1" || T.to_bytes(8, 'big') || nonce.encode('ascii') || H_bytes
   Total length = 5 + 8 + 32 + 32 = 77 bytes
6. Sign S_content using RSA-PSS:
   Signature = K_priv.sign(
       data = S_content,
       padding = padding.PSS(mgf=padding.MGF1(hashes.SHA256()), salt_length=padding.PSS.MAX_LENGTH),
       algorithm = hashes.SHA256()
   )
7. Serialize Public Key K_pub to PEM string.
8. Construct and return JSON package with Base64-encoded message and signature.
```

### 14.2 Verification Algorithm

```
Input: Signature Package P, Optional Trusted Public Key K_trusted, Boolean check_replay, Optional max_age
Output: VerificationResult (VALID | INVALID | REJECTED, reason)

1. Structural Check: Ensure all mandatory fields exist (version, algorithm, timestamp, nonce, message_sha256, message_b64, signature_b64, public_key_pem).
   If missing or version != 1 -> Return INVALID.
2. Base64 Decode: Decode message_b64 -> M_bytes, signature_b64 -> Sig_bytes.
   If decoding fails -> Return INVALID.
3. Timestamp Freshness Policy Check:
   age = current_time - P.timestamp
   If max_age specified and age > max_age -> Return REJECTED.
   Else if check_replay enabled and age > 300 seconds -> Return REJECTED.
4. Replay Store Check:
   If check_replay enabled and P.nonce in NonceStore -> Return REJECTED.
5. Public Key Resolution:
   Load K_embedded from P.public_key_pem.
   If K_trusted is provided:
       Compare serialized PEM bytes of K_trusted and K_embedded.
       If mismatch -> Return INVALID ("Embedded public key does not match trusted key").
6. Message Hash Verification:
   Compute H_computed = sha256_hex(M_bytes).
   If H_computed != P.message_sha256 -> Return INVALID ("Message SHA-256 mismatch").
7. Cryptographic Signature Verification:
   Reconstruct S_content = b"DSVS1" || P.timestamp.to_bytes(8, 'big') || P.nonce || bytes.fromhex(P.message_sha256)
   Verify Sig_bytes over S_content using K_embedded with RSA-PSS (MGF1-SHA256, MAX_LENGTH).
   If InvalidSignature exception raised -> Return INVALID.
8. Replay Store Update:
   If check_replay enabled:
       Add P.nonce to NonceStore.
9. Return VALID.
```

### Field Specification Table

| Field Name | Data Type | Description |
|---|---|---|
| `version` | `integer` | Format version identifier (fixed to `1`). |
| `algorithm` | `string` | Cryptographic signature specification label (`"RSA-PSS-SHA256"`). |
| `filename` | `string` | Original file name if a file was signed; empty string for inline text. |
| `timestamp` | `integer` | UTC Unix epoch time (in seconds) recorded at the moment of signing. |
| `nonce` | `string` | 32-character hexadecimal string representing 16 random bytes (128 bits of entropy). |
| `message_sha256` | `string` | 64-character hexadecimal SHA-256 digest of the unencoded message bytes. |
| `message_b64` | `string` | RFC 4648 Base64-encoded string of the raw message or file bytes. |
| `signature_b64` | `string` | RFC 4648 Base64-encoded string of the raw RSA-PSS signature bytes. |
| `public_key_pem` | `string` | X.509 SubjectPublicKeyInfo PEM string representing the signer's public key. |

## 16. Verification Results

The verification engine classifies all evaluation attempts into three deterministic categories:

```
                                Verification Request
                                         │
                 ┌───────────────────────┼───────────────────────┐
                 ▼                       ▼                       ▼
            ┌─────────┐             ┌─────────┐             ┌──────────┐
            │  VALID  │             │ INVALID │             │ REJECTED │
            └─────────┘             └─────────┘             └──────────┘
```

| Result Category | Semantic Meaning | Common Causes |
|---|---|---|
| **`VALID`** | Cryptographic verification succeeded AND all enabled security policies passed. | Unaltered message, valid signature, trusted key match, fresh timestamp, unique nonce. |
| **`INVALID`** | Cryptographic or structural integrity check failed. | - Modified message bytes<br>- Altered message hash<br>- Corrupted signature bytes<br>- Tampered timestamp or nonce within signed content<br>- Key mismatch (embedded key $\ne$ trusted key)<br>- Signature produced by untrusted private key<br>- Missing or malformed package JSON fields |
| **`REJECTED`** | The signature is mathematically authentic, but violates operational security policy. | - **Replay Attack:** Nonce has already been recorded in the state store.<br>- **Expired Signature:** Signature timestamp exceeds the allowed `max_age` or default window. |

### Mathematical Validity vs. Application Rejection

> **Why a mathematically valid signature can be REJECTED:**  
> In a replay attack, an adversary captures an authentic signature package transmitted by Alice and sends an exact copy to the server later. Because the cryptographic signature and hash remain unaltered, the RSA-PSS equation verifies successfully. However, the system **rejects** the package because the nonce was already consumed or the timestamp expired, protecting against replay attacks.

## 18. Security Considerations

### 18.1 Cryptographic Algorithms & Parameter Choices

- **RSA-PSS vs. PKCS#1 v1.5:** RSA-PSS is a randomized, provably secure signature scheme. Unlike deterministic PKCS#1 v1.5 padding, RSA-PSS incorporates a random salt for every signature, preventing signature forgery attacks.
- **SHA-256 Digest:** Provides 128-bit collision resistance and 256-bit preimage resistance. Weak algorithms such as MD5 and SHA-1 are not supported.
- **Salt Configuration:** Configured to `padding.PSS.MAX_LENGTH` to maximize probabilistic entropy.

### 18.2 Private Key Security

- **In-Memory Web Processing:** When using the web UI, private keys are processed ephemerally in RAM and are never persisted to server disk storage.
- **Passphrase Encryption:** Private keys saved to disk should use passphrase encryption via `serialize_private_key(..., password=...)`.
- **POSIX Permissions:** Key generation scripts apply `chmod 0o600` on POSIX systems to restrict read access.
- **Production Key Storage:** Production systems should utilize Hardware Security Modules (HSMs) or OS keyrings rather than plaintext disk storage.

### 18.3 Public-Key Trust & Identity Binding

The signature package embeds the signer's public key for technical self-containment. However, **the embedded key alone does not authenticate the sender's identity**.

```
Attacker generates Evil_Priv / Evil_Pub ──► Signs message ──► Embeds Evil_Pub in package
                                                                        │
Without trusted key validation: Receiver verifies with Evil_Pub  ──► VALID (Attacker succeeds!)
With trusted key validation:    Receiver checks against Alice_Pub ──► INVALID (Attack blocked!)
```

> **Important Security Rule:** A signature verified *only* against the package's embedded public key proves internal consistency, but does not prove who generated the key. Genuine sender authentication requires validating the public key against a trusted local store, a pre-shared key list, or an X.509 Certificate Authority (CA).

### 18.4 Replay Protection Architecture

Replay protection requires four synchronized controls:
1. **Signed Nonce:** A 128-bit random value (`secrets.token_hex(16)`) included in the signed payload.
2. **Signed Timestamp:** Unix epoch time bound into the signed payload.
3. **Freshness Checking:** Rejection of signatures older than `MAX_SIGNATURE_AGE` ($300\text{s}$).
4. **Stateful Replay Store:** Tracking previously accepted nonces. Nonces are recorded **only after** all cryptographic and freshness checks succeed.

### 18.5 TLS vs. Digital Signatures

| Property | Transport Layer Security (TLS) | Digital Signatures (RSA-PSS) |
|---|---|---|
| **Layer** | Transport Layer (Hop-by-hop channel) | Application Layer (End-to-end object) |
| **Protection Scope** | Protects data in transit between socket endpoints | Protects the data object persistently across storage and forwarding |
| **Confidentiality** | Encrypts network packets | Does not encrypt message content |
| **Persistence** | Security terminates when the TLS connection closes | Signature remains verifiable at rest, offline, and through intermediaries |

### 18.6 Audit Log Integrity

The audit log (`logs/audit.jsonl`) provides an append-only event record for monitoring. Because it resides on the local filesystem, it is not inherently tamper-proof against privileged local attackers. Production systems should stream audit logs to a remote, write-once logging server or SIEM.

### 18.7 Web Application Security

The included Flask application is designed for educational demonstrations. Deploying this system in production requires additional hardening:
- Enforce HTTPS and secure cookie flags.
- Implement API authentication (OAuth2 / JWT) and authorization controls.
- Enforce Cross-Site Request Forgery (CSRF) protection.
- Implement rate limiting to prevent denial-of-service and brute-force key generation.
- Enforce strict upload file-size limits and virus scanning on binary files.

## 19. Advantages

- **Strong Cryptographic Assurance:** Built on RSA-PSS and SHA-256 adhering to modern standards.
- **Broad File Compatibility:** Seamlessly signs and verifies both plaintext messages and arbitrary binary files up to 50 MB.
- **Multi-Modal Access:** Operates via a modern 4-tab web dashboard, CLI tools, or TCP client/server network sockets.
- **Demonstrable Attack Resistance:** Includes test vectors for message tampering, signature corruption, key substitution, and replay attacks.
- **Structured Auditability:** Append-only JSON Lines logging enables traceability across all interfaces.
- **100% Automated Test Coverage:** 46 automated unit and integration tests covering cryptographic edge cases, APIs, and network protocols.

## 20. Limitations

- **In-Memory Replay Store:** The server's nonce tracking store is held in memory and is cleared upon process restart.
- **No Native PKI / CA Validation:** Key trust relies on manual pre-shared public key distribution (`--pub`) rather than hierarchical X.509 certificate chain validation.
- **File-Based Key Storage:** Private keys are stored as PEM files on disk rather than inside a Hardware Security Module (HSM) or secure enclave.
- **Self-Signed TLS Certificates:** The demo TLS certificate generated by `gen_cert.py` is self-signed and not trusted by default browser root stores.
- **No User Account Management:** The Flask interface operates session-free without multi-tenant authentication or access control lists.
- **Local Audit Log:** The local JSON Lines log file is not cryptographically anchored or tamper-proof against local filesystem modification.

## 21. Future Scope

- **X.509 PKI & Certificate Chain Validation:** Implement full hierarchical certificate verification against root and intermediate Certificate Authorities with CRL/OCSP revocation checks.
- **Elliptic Curve Cryptography (ECC):** Add support for ECDSA (NIST P-256 / P-384) and Ed25519 (EdDSA) signature algorithms for smaller signatures and faster computation.
- **RFC 3161 Trusted Timestamping:** Integrate with external RFC 3161 Timestamp Authorities (TSA) to prove signatures existed at a verifiable point in time.
- **Persistent Database-Backed Replay Store:** Replace in-memory nonce tracking with a persistent database (PostgreSQL / Redis) with automatic TTL eviction.
- **Hardware Security Module (HSM) Support:** Integrate PKCS#11 interfaces to generate and store private keys within hardware tokens (e.g., YubiKey, AWS CloudHSM).
- **Production API Hardening:** Add OAuth2 authentication, rate limiting, and containerized deployment configurations (Docker, Kubernetes).
