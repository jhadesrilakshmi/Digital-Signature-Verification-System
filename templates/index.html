Security Architecture

Core Cryptographic Components

RSA-PSS

Digital signature algorithm used to authenticate and protect signed data.

SHA-256

Cryptographic hash used to detect message modification.

Timestamp + Nonce

Provides freshness information and supports replay protection.

Trusted Public Key

Used by the receiver to verify the expected signing key.

Verification Checks

Receiver Validation Pipeline
Package Structure
Verifies JSON envelope schema, mandatory fields, and Base64 format integrity.
Trusted Public Key
Embedded public key is compared against the receiver's trusted public key anchor.
Message Integrity
SHA-256 hash is recomputed from payload and compared with the signed digest.
RSA-PSS Signature
Signature is mathematically verified using the trusted RSA public key and MGF1 salt.
Timestamp Freshness
Signature creation timestamp is verified against maximum allowed age threshold.
Replay Protection
Cryptographic 128-bit nonce is validated against previously accepted nonces store.

Verification Result States

Standard Output Classification
VALID
All required cryptographic and security checks passed. Authentic and untampered.
INVALID
The package failed a structural or cryptographic validation check. Tampered or forged.
REJECTED
The package may be cryptographically valid but was rejected because of freshness or replay policy.

All attack simulations are executed locally against real cryptographic primitives and log real events into the Audit Log and Dashboard counters.

    

  


  

    
    

      

        
Attack 1: Message Tampering

        NOT RUN
      

      

        Attacker Action: Intercepts package in transit and alters the message content (e.g. changes payment amount).
        


        Detection Mechanism: The receiver re-computes SHA-256 over received message. The computed hash fails to match the signed hash.
      

      
      

    


    
    

      

        
Attack 2: Signature Corruption

        NOT RUN
      

      

        Attacker Action: Injects bit-flips or noise into the raw RSA-PSS signature bytes during transmission.
        


        Detection Mechanism: RSA-PSS verification mathematically rejects the corrupted signature against the public key.
      

      
      

    


    
    

      

        
Attack 3: Public-Key Substitution

        NOT RUN
      

      

        Attacker Action: Attacker generates their own RSA key pair, signs a malicious message, and embeds their public key in the package.
        


        Detection Mechanism: Receiver compares the embedded key with Alice's pre-distributed trusted key; the mismatch aborts verification.
      

      
      

    


    
    

      

        
Attack 4: Replay Attack

        NOT RUN
      

      

        Attacker Action: Eavesdrops on a valid signed transfer and replays the identical package to execute a second transaction.
        


        Detection Mechanism: Server nonce store accepts the 1st submission, then marks the nonce consumed. 2nd submission is rejected.
      

      
      

    


    
    

      

        
Attack 5: Timestamp Manipulation

        NOT RUN
      

      

        Attacker Action: Modifies the timestamp field to make an old/expired signature appear freshly created.
        


        Detection Mechanism: The timestamp is bound into the RSA-PSS signed content. Altering the timestamp invalidates the signature.
      

      
      

    


    
    

      

        
Attack 6: Signature Removal

        NOT RUN
      

      

        Attacker Action: Strips the signature field entirely or submits a malformed signature package missing required cryptographic attributes.
        


        Detection Mechanism: Package schema validation detects missing signature fields before cryptographic processing.

🛡️ Two Layers of Defense: Digital Signatures vs TLS

      Defense-in-Depth
    

    

      

        
🔐 Digital Signature (RSA-PSS)

        
    
          
  • ✔ Application-Level: End-to-end authenticity and integrity.
    • 
          
  • ✔ Persistent Security: Data remains verifiable at rest, in storage, and after multiple hops.
    • 
          
  • ✔ Attribution: Binds message directly to signer's private key.
    • 
          
  • ✔ Offline Capable: Can be verified without an active network connection.
    • 
        

      

      

        
🌐 TLS Transport Security

        
    
          
  • ✔ Transport-Level: Hop-by-hop confidentiality and eavesdropping prevention.
    • 
          
  • ✔ Transient Protection: Data is encrypted only during transit through the wire.
    • 
          
  • ✔ Channel Security: Protects the communication pipe, not the document itself.
    • 
          
  • ✔ Complementary: Signatures secure the content; TLS secures the pipe.
    •
